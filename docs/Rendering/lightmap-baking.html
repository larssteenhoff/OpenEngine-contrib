Baked diffuse GI and directional shadow lightmaps

The experimental lightmap-baking package is disabled by default. Enable it in the Package Manager and reopen the project, or add "enabled": ["lightmap-baking"] to the project's Packages/manifest.json. An explicit disabled entry takes precedence. Baking is an editor package; the engine's default real-time lighting is unchanged.

The package implements UV-space lightmapping. It writes two textures per static receiver:

- A linear visibility PNG for the primary directional light. White is lit; black is occluded. A disk of rays produces soft shadows from the light's angular diameter.

- An HDR RGB texture containing diffuse irradiance divided by pi. Cosine-weighted path tracing includes bounced directional/point/spot light, emissive surfaces, vertex colours, albedo/metallic/emissive textures, and an optional environment. Direct lighting and specular reflections remain live.

The default bake is 1024×1024, 256 GI samples per subtexel, with denoising enabled. Scrambled Hammersley sampling spreads the first-bounce rays evenly. A variance-guided, three-pass à-trous filter smooths diffuse noise while respecting UV charts, world positions and normals. It runs before padding and does not blur the directional shadow texture. Set denoise=false for an unfiltered reference bake. Filtering can soften fine indirect detail; increase samples and resolution when that detail matters.

Surfaces/shadow_lightmap_pbr.glsl samples both through UV1. Baked irradiance replaces the diffuse environment/DDGI term on that receiver, including the ambient floor, so indirect lighting is not counted twice. Other meshes continue using the existing lighting pipeline. receiveShadows=false disables the baked directional mask too.

This is an adaptation to this engine's scene, BVH and material systems, not the complete Godot LightmapGI subsystem. It does not include directional SH lightmaps, GI probes for moving objects, automatic UV unwrapping/atlas packing, or Godot's denoising/seam-blending passes.

Prepare the scene

Use static, opaque Standard PBR meshes with a non-overlapping second UV channel (UV1) entirely inside [0,1]. Give separate charts a gutter of at least twice the bake padding, measured in texels. Padding expands into empty texels; sampling explicitly uses mip zero to avoid chart bleeding. Export UV1 from the modelling tool; the baker does not change the source model. Receivers with LODs that have independent vertex/UV streams are rejected.

Choose receiver meshes and any additional static occluders. Receivers are automatically included as occluders. Every selected mesh must cast shadows. Skinned meshes, morph targets, procedural terrain, vertex modifiers, alpha-cutout/blended/transmissive materials, custom surface graphs, and hex tiling are rejected or outside the mesh input contract. Additional lights support directional, point and spot types; punctual bounce lights currently require physical inverse-square falloff. Emissive meshes can represent area emitters.

All material inputs are snapshotted before the worker starts. Texture sampling supports source images decodable by stb_image, including PNG/JPEG/HDR; cooked GPU-only texture files are not decoded. The bake uses diffuse material reflectance rather than tracing specular/clear-coat lobes.

Bake in the editor

1. After enabling the package, choose Tools → Lighting Bake (the registered panel also appears in the Panels menu).

2. Click Add scene receivers to collect eligible meshes automatically, or select meshes/model roots in the hierarchy and click Add selected receivers. The scene scan skips unsupported geometry/materials and meshes without UV1, and reports skipped names and reasons. Existing baked meshes remain eligible for rebaking. Mesh children are included for manual selection. Receivers need the second UV set described above.

3. Leave Scene occluders enabled to use the scene's static shadow-casting meshes for occlusion and bounced light. To choose these explicitly, turn it off and use Add selected occluders. Receivers always participate too.

4. Keep the 1024 resolution, 256 GI samples, two bounces and denoising defaults, or choose a resolution up to 8192×8192 (8K). The panel uses the scene's primary directional light and displays its name.

5. Click Bake lighting. The baker automatically uses GPU ray queries when supported, and the progress label shows GPU or CPU. Progress updates within each mesh. Cancel stops the job and keeps existing materials. Baking continues if the panel is closed.

6. When the panel reports that the baked materials were applied, save using the editor’s normal Save action.

Advanced contains shadow samples, the live-shadow fade range, uniform ambient light and an optional environment image path. The panorama path may be absolute or relative to project assets. The scene sky is not captured automatically. With diffuse GI disabled, the job only bakes the directional shadow texture.

Meshes and materials are checked before baking; errors identify the mesh to fix. Switching scenes or entering playback cancels a pending bake and clears the panel's mesh selection. Geometry, source assets or light changes during a bake prevent automatic material assignment. The panel and automation tools share one job and the same output handling.

Editor automation

The MCP/CLI tools bake_lightmaps, get_lightmap_bake, and cancel_lightmap_bake wrap the editor debug server. Rebuild the MCP package to expose the added tools. The debug server accepts these commands (the same JSON request transport as other editor automation):

{
  "id": 1,
  "method": "bake_lightmaps",
  "params": {
    "receivers": [123, 456],
    "occluders": [789, 1011],
    "lightEntity": 42,
    "resolution": 1024,
    "giSamples": 256,
    "denoise": true,
    "useGpu": true,
    "bounces": 2,
    "shadowSamples": 32,
    "padding": 4,
    "bias": 0.001,
    "environmentRadiance": [0.03, 0.04, 0.06],
    "shadowMode": "Overlay",
    "fadeStart": 40,
    "fadeEnd": 50,
    "apply": true
  }
}

Entity IDs above are examples. lightEntity must be the scene's primary directional light. Set the fade range inside the live directional shadow distance. Modes match Godot's shadowmask equations:

ModeNear cameraBeyond fade end
ReplaceLive shadowsBaked shadows
OverlayBaked × live shadowsBaked shadows
OnlyBaked shadowsBaked shadows

For a panorama, replace environmentRadiance with environmentTexture (asset GUID or source image path), and optionally set environmentIntensity and environmentRotationDegrees. Mapping matches the engine's latitude/longitude sky capture. The environment is explicit: the baker does not automatically capture the current procedural atmosphere, skybox or ambient floor. Omitted environment input is black. A panorama containing the sun can double-count it alongside the directional light; use an environment with the sun removed when that matters.

The start call returns immediately with status: "baking" and a jobId. Poll get_lightmap_bake until complete; while baking it reports progress in [0,1], completedReceivers, totalReceivers, cancelling and acceleration (gpu_ray_query or cpu). The editor imports completed outputs and, with apply=true, assigns the generated materials using normal editor component-commit notifications, even when the panel is closed and no client polls. It declines assignment when selected geometry, source asset files, material assignments, or captured lights changed during the bake. cancel_lightmap_bake requests cancellation. Only one bake is active at a time. Bakes cannot start during playback.

Completed results and bake.json record gpuTracedRays, tracedRays and the actual acceleration (cpu, gpu_ray_query, or gpu_and_cpu after a partial GPU fallback). Set useGpu=false to force CPU tracing for comparisons.

Outputs are stored in the current project's Assets/Lightmaps/<jobId>/: one .material, _shadow.png, and _indirect.hdr per receiver, plus bake.json. Each job creates new assets, leaving existing materials and models intact. Save the scene after assignment to persist the material references. These are ordinary asset dependencies and follow normal player packaging. apply=false saves/imports without changing mesh assignments.

giSamples=0 requests shadow-only baking. GI supports up to 16 diffuse bounces. Editor jobs accept 1–4096 receivers, up to 4096 explicitly listed occluders, and resolutions up to 8192. The package baker supports up to 8192² texels. Receivers bake sequentially; 8K uses 64 times as many texels as 1024, with correspondingly higher memory and bake time. A 64²/64-sample unfiltered bake is useful for testing the workflow, but is not a visual-quality preset. Use the defaults for review; increase to 512–1024 samples for larger surfaces or closer inspection. Small emissive sources need more samples because emissive lighting is discovered by path hits. Bake time grows with resolution squared and sample count.

Bakes are static snapshots. Rebake after geometry, material, environment or light changes. Rotating the sun automatically disables its mismatched shadowmask; the baked GI still needs rebaking. There is no automatic invalidation of baked lighting after assignment, and the source-asset check during a bake uses file modification times.

Package architecture and validation

Packages/lightmap-baking/Editor/Baker/ShadowLightmapBaker.h exposes BakeShadowLightmap, ShadowLightmapMesh, bake options and the result. Pass final model-to-world matrices (including source-node transforms), static occluders, and optional material/environment samplers. The output is unchanged on validation failure or cancellation. Set options.CreateRayTracer=CreateGpuLightmapRayTracer to select GPU acceleration in a package host; leaving it empty selects CPU. The editor shares one GPU BLAS/TLAS across the job’s receivers on a private headless device. It uses the enabled ray-query capability and a descriptor-bound acceleration structure on Metal/Vulkan, allowing the driver to use dedicated ray-tracing hardware where available. A GPU without ray-query support uses the CPU BVH.

Directional visibility, diffuse path intersections and bounce-light shadow rays are submitted in batches of at most 65,536 rays. Path working memory is bounded independently of atlas size. Material/environment callbacks and denoising remain on the CPU, so texture evaluation and supported lighting match both paths. GPU allocation, compilation or submission failures retry the affected batch on the CPU and keep subsequent tracing there. Cancellation is checked between batches; an in-flight GPU batch must finish before its resources are released. No editor render-thread buffers or scene acceleration structures are shared with the baker.

The CPU BVH is built once per receiver bake and shared by its visibility and GI rays. Sampling is deterministic for identical inputs; minor floating-point intersection differences between GPU and CPU can affect edge hits.

Build and run ShadowLightmapBakerTests for numerical coverage, CPU fallback/cancellation, and live GPU tests for clipped closest hits, barycentrics, double-sided geometry, frame reuse, and textured multibounce agreement. GPU tests skip when ray queries are unavailable. ShadowLightmapBakerTests --gtest_filter=LightmapSurfaceCompose.* compiles the actual surface across forward/clustered/IBL/DDGI and missing-UV variants. These tests exercise core algorithms and shader compilation; they do not replace visual inspection of the chosen scene and unwraps.

The source reference is the local Godot checkout's modules/lightmapper_rd/lm_compute.glsl, lightmapper_rd.cpp, and servers/rendering/renderer_rd/shaders/forward_clustered/scene_forward_clustered.glsl. The Godot MIT notice is retained in Packages/lightmap-baking/Licenses/Godot-MIT.txt.

Package boundaries

The editor module owns the CPU/GPU baker, bake service, panel, and automation commands. It registers the panel through EditorPanelRegistry and receives host lifetime and scene invalidation through EditorPluginRegistry. Jobs continue with the panel closed, cancel before scene replacement/playback, and finish shutting down before engine teardown. No lightmapper panel factory, bake service, or command handler is embedded in EditorApplication.

Player receives the package's material surface and generated ordinary texture/material assets, not the baking module. The surface owns the directional shadowmask equations and irradiance state. The shared renderer supplies generic material lighting hooks; ordinary materials use identity/default hooks. Generated materials enable CUSTOM_LIGHTING and use the existing user uniform lanes, without adding lightmap names to the core material parser or property table.

Source attribution and the required MIT license remain in the package's Licenses directory and the staged notices. Moving code does not remove attribution obligations.

The editor integration fixture lives in Tests/EditorHarness/lightmap-baking; use a copied project and a dedicated editor debug port. The fixture explicitly enables the package. Run its run-checks.mjs and run-ui-checks.mjs with --project pointing at that copy; --require-gpu requires all rays to use GPU queries. The SDK lifecycle suite covers late loading, disable/re-enable, replacement, command dispatch, and shutdown. Package resolver coverage checks that the disabled-by-default package cannot load without opt-in.
